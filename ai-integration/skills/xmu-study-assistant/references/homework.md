# 作业处理

定位课程和活动ID，调用 `get_assignment` 读取要求、教师附件、已有正文和用户附件。保留已有成果；任务或课程目标不唯一时先消歧。

## 理解与生成

通过 `download_assignment_attachment` 获取教师附件，再按题目选择 `list_course_materials` 和 `list_local_materials` 中相关的课件。检查格式、命名、截止时间、实验环境、模板和评分要求。分组作业可以继续开展整理和本地创作，MCP 目前只支持个人作业写入。

在当前账号工作目录下按课程/作业建立成果目录。已有运行环境时执行必要实验或代码验证；需要额外数据、授权软件、真实测量或硬件时，明确哪些部分已做、哪些仍缺条件。不要生成虚构的测试成功、实验截图或采集结果。

使用当前客户端已有的文件、终端、Office/PDF工具生成所需格式。MCP 能传递资料和成果，不能代替客户端缺失的编译器、运行环境或文档生成器。登记成果时填写所属 course_id、activity_id。对照要求核对代码、报告、附件和命名；给出可打开的成果与验证说明。

## 草稿和正式交付

作业允许附件时，优先用附件交付，新作业的正文留空，提交说明写在聊天预览里。更新已有作业时保留用户原正文，除非用户要求清空。若用户或作业要求明确指定正文，按要求填写，并在写入前的预览中提醒一次：“畅课可能把正文转成 PDF，网页附件栏里可能多出一项，名称有时显示为空。”接着沿用原有的确认流程。

本地交付、平台草稿与正式交付按用户目标处理。「给我方案」「先写好，别交」只保存本地。明确要求平台草稿时使用 `draft`。用户直接委托「完成这个作业」「做完并交」且没有限定只做方案或本地时，完成并验证成果后准备正式交付，最后由用户决定是否交。

1. 用 `prepare_submission` 生成本地预览。核对课程、作业、正文、文件名和保留或移除的附件。省略 `content_html` 保留原正文，传空字符串清空，默认保留原附件。只添加已登记的成果文件。
   - 用户明确要求仅交正文时，传正文、`file_ids=[]` 和 `keep_existing=false`。在预览里确认用户附件数为 0，并列出会移除的旧附件。平台可能生成正文预览，单独报告回执的 `platform_text_preview_count`，不要当作用户上传的附件。
2. 向用户展示最终内容或其可打开的本地文件、实际验证结果、课程、作业、附件和是否更新已有记录。给出这些信息后再调用工具。此时无需再发一条聊天确认，`commit_submission(plan_id, mode="submit")` 会直接打开 Windows 确认窗口。提醒用户核对后自行确认。AI 不得代按或自动点击。
3. `get_status` 如果明确表示正式提交不可用，停在本地预览并说明原因。用户取消时也停在本地。用户只要求平台草稿时才直接用 `commit_submission(plan_id, mode="draft")`。后来要正式交付时，基于现有草稿重新生成计划，已在平台的附件通过保留选项沿用。
4. 收到 `confirmed` 且回执模式为 `submit` 才报告正式交付成功。收到 `failed_before_submit` 时说明正式请求尚未开始，可能有临时上传的文件。调用超时或结果待核实时先用 `get_submission_status(plan_id)`，按需用 `get_assignment` 查看现状。即使允许重新准备，也要先核实平台状态，避免重复交付。

平台记录或成果文件变化后重新生成预览，账号切换后重新定位作业，过期计划重新读取后再准备。保持在 MCP 流程，禁止以浏览器、原平台界面、脚本或同一作业的新计划绕过确认或未知回执。MCP 不支持的平台功能，由用户自行处理。
